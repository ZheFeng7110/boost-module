# Release Notes — v1.92.0.0.0.0

> 日期: 2026-10-10 · 目标上游: Boost 1.92.0 (`BOOST_VERSION 109200`)
> **正式版** (模块封装版本 0.0.0; Boost 1.92 线的首个版本)。模块/feature 计数与可消费面
> 与上一线形态一致: **116 模块 / 118 feature / 默认 49 库闭包**。本周期重导上游
> Boost 1.92.0 并重生成导出面, 补全发布自动化 (GitCode 镜像 + mcpp package index),
> 刷新 CI, 并新增一处 macOS 异常处理绕行。完整增量见 §3。

## 1. 这是什么

使用 [mcpp](https://github.com/mcpp-community/mcpp) 构建工具对 Boost 库做的
C++23 named modules 封装: 消费者 `import boost.filesystem;`
（或汇总 `import boost;`）, API 拼写与上游一致, 无需 `#include`。

这是 Boost **1.92.0** 线的首个正式版, 继 `1.91.0.0.1.0` (2026-09-22) 之后发布;
模块面按新上游头文件重生成, 但模块/feature 计数与可消费集合不变。mcpp package index
集成 (T3) 现已纳入自动发布流程, 因此本版本既可通过 registry 消费, 也可继续用
git 依赖（§5）。

## 3. 自 v1.91.0.0.1.0 以来的变更

### 3.1 上游 Boost 1.92.0 重导与导出面重生成

- **vendored 上游 `1.91.0 → 1.92.0`**（`BOOST_VERSION 109200`、
  `BOOST_LIB_VERSION "1_92"`）: `deps/boost/` 从官方 tarball 重导, 全部 vendored 补丁
  重放（`scripts/reapply_hand_edits.py`）, 并全量重生成已提交的产物
  （`src/gen_exports/*.inc` / `*.deps`、`src/*.cppm`、`mcpp.toml [features]`、
  `scripts/features.lst`）。
- **头集重扫（`scripts/libs.json`）**: 纳入 1.92 在目标库下新增的头文件
  （如 `asio/fwd.hpp`; 49 个 `container/experimental/segmented_*`; `graph`、`lockfree`
  新增项）, 恢复历史 curated 排除项, 移除已移出目标集的库。实际导出面发生变化的库为
  **asio / container / graph / lockfree**, 其余不变。
- **`decimal` 平台守卫**: Boost 1.92 新增了一批只在特定编译器/架构存在的
  `detail`/int128 实体（`u256_add` / `add_carry_u64` 在 `__GNUC__` 下;
  `BOOST_DECIMAL_DETAIL_INT128_HAS_FAST_DIV128` 一族在 x86-64 GCC/Clang/MSVC 下）。
  MinGW 快照把两者都导出了, 导致 macOS arm64 与 windows-msvc 上
  `import boost.decimal;` 编译失败; 现按上游条件包裹对应 `using` 行。
- **`stacktrace` feature** 增编 `deps/boost/libs/stacktrace/src/dump.cpp`
  （1.92 把 `this_thread_frames::collect` 从头文件移入独立 TU）, 保持 `basic` 面可链接;
  `stacktrace` 仍为 `basic` 形态。
- **`asio` vendored 补丁由 6 文件缩为 2**: 上游 1.92 已把
  `prefer` / `query` / `require` / `require_concept` 对象在 C++17+ 下改为
  `inline constexpr`, 仅 `call_stack.hpp` / `keyword_tss_ptr.hpp` 的静态成员定义仍需
  `inline` 修补。

### 3.2 macOS 异常处理绕行

- **macOS 改用 Apple 链接器**（`[target.macos.build]` → `-fuse-ld=/usr/bin/ld`）。
  LLVM 22.1.8 的 `ld64.lld` 可能生成重复的 `__unwind_info` 条目（零编码遮蔽真实编码）,
  使 libunwind 在第一阶段即停止、所有 handler（含 `catch (...)`）都不可达; CI 上表现为
  `program_options` 非法值用例 abort, 而 Apple 链接器产物正常。`ld64.lld` 会忽略
  `-no_compact_unwind`, 故以换链接器作为绕行（上游
  [LLVM issue 216154](https://github.com/llvm/llvm-project/issues/216154)）。
- **`program_options` 回归覆盖拆分为** 模块侧用例
  （`tests/program_options.cpp`, 在 linux/windows/macOS 上仍精确捕获
  `invalid_option_value`）+ 独立 include-only 可执行
  （`tests/program_options_invalid_value.cpp`）。测试计数现为 **142**（原 141）。

### 3.3 发布自动化补全

- **GitCode 镜像 job**: 稳定/预览 tag 下, 待 GitHub Release 生成后, workflow 把全部分支/
  tag 强制同步到镜像 `gitcode.com/ZheFeng7/boost-module`, 并发布内容一致的 Release,
  Release Note 取自 `docs/zh/release_notes/<tag>.md`（标题 / 预发布标志 / 附件与 GitHub
  相同）。
- **mcpp package index (T3) 登记**: 非预览 tag 下新增 job, 在 `mcpp-index` fork 的分支上
  向 `pkgs/z/ZheFeng7110.boost.lua` 前插新版本并向上游开登记 PR。该步骤把包发布到 mcpp
  index; release 标题现直接使用 tag（去掉了 `Release ` 前缀）。

### 3.4 CI 与文档

- **CI 刷新**: mcpp 钉到 `2026.10.8.1`; runner 系统版本更新; 新增 Linux ARM64 (gcc) 腿;
  移除无 mcpp 发行资产的宿主（macOS x86_64、Windows ARM64、Linux ARM64 LLVM）。矩阵为
  5 条测试腿 × A/B 两组, 外加门禁 examples job。
- **文档/示例**: 以 mcpp package index 作为首选消费渠道（git 依赖作为备选, 并注明中国
  大陆镜像地址）; `examples/git_dep_usage` 指向 1.92 升级 revision。

无模块、feature、默认闭包或 API 拼写变更; 支持的库集合不变。

## 4. 已知限制（仍然有效）

正式版从简列出; 逐条明细与逐库说明见[架构文档 §4](../architecture.md#4-已知限制-消费者须知)。

- **工具链硬限制**: clang 2^31 源位置上限使 `--features all` 不可行（约 2.98GB CMI）——
  逐库 import; 特性宏除 `backend-*` profile 子集外均为构建期固定。
- **上游形态固定**: filesystem v3 / thread v2 / stacktrace basic。
- **未打包**: iostreams 外部后端（zlib/gzip/bzip2/lzma/zstd）与 cobalt ssl（OpenSSL）;
  math tr1; container `dlmalloc`/`alloc_lib`; process 聚合头; log 的手写 `mc.exe`
  event_log stub。
- **gcc 16.1 缺陷家族**（编译器缺陷, 已绕行或规避）: exception CMI pendings、variant
  `apply_visitor` free-function ICE、消费者自定义异常缺 `clone_impl` thunk、
  CMI/GMF 合并冲突。三模式消费规则见架构文档 §4.2。
- **纯 include-only 集合（20 库, 无 feature/模块）**: 宏驱动 16
  （preprocessor / mpl / fusion / proto / spirit / xpressive / typeof / vmd / phoenix /
  parameter / metaparse / function_types / tti / local_function / msm / foreach）+
  降级 4（exception / describe / openmethod / scope_exit）。
- **平台缺口**: mingw（无 CI 腿; thread `sleep_for` 挂起、url `BOOST_URL_RETURN_EC`
  冲突）与真 MSVC (cl) 不承诺; macOS 精确异常捕获仍可能受 Mach-O typeinfo 不跨模块
  合并影响。
- **M13 暂缓（11 库）**: context / fiber / coroutine (asm)、locale (ICU)、mpi、
  python、parameter_python、graph_parallel、compute (OpenCL)、mysql / redis
  (OpenSSL)。
- **未启用上游 C++20 模块**: Boost 1.92 若干库自带 `modules/`; 本封装仍导出自己的
  `export using` 层, 未消费之。

## 5. 打包状态

正式版门槛中的 mcpp package index 步骤（T3: 描述符集成 + registry 消费）现已自动化:
发布 workflow 在 mcpp index 上登记 `ZheFeng7110.boost` 新版本并向上游开 PR, 文档以
registry 作为首选渠道。源码归档（`.zip` / `.tar.gz` / `.tar.xz` / `.7z` + `.sha256`）
由发布 workflow 生成, 并在 GitCode 镜像同一份附件。消费者也可继续使用使用文档所述的
git 依赖。

## 6. 报告问题

提交 issue 前, 请先区分**封装问题**与**编译器缺陷**:

1. **gcc 16.1 缺陷家族**（§4）属编译器缺陷; 请附可上游复现的最小示例并注明编译器版本。
2. **clang/llvm 问题**（如 2^31 源位置上限、macOS `ld64.lld` unwind 缺陷）属工具链限制,
   封装层会力所能及地绕行。
3. **疑似封装问题**（缺实体 / 拼写不符 / 链接错误 / 文档与行为矛盾）: 请附编译器 + 平台 +
   依赖声明 + 最小复现 TU。
4. mingw / 真 MSVC（非承诺范围）的失败反馈同样欢迎。
