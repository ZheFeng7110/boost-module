# boost-module Architecture

> Date: 2026-09-09 · Audience: consumers · Content extracted from the
> [consolidated design](../../.agents/docs/2026-09-08-consolidated-design.md)
> (that document is authoritative)
> Target upstream: **Boost 1.91.0** (`BOOST_VERSION 109100`)

## 1. Project Positioning

C++23 named modules wrapper for the Boost libraries built with the
[mcpp](https://github.com/mcpp-community/mcpp) build tool: Boost's header-based API is
exported as module interfaces (`.cppm` + `export namespace boost { using ...; }`), so
consumers can `import boost.filesystem;` (or the umbrella `import boost;`). The API spelling
is identical to upstream — no `#include` needed.

- **Scale** (2026-09-09, after C5): 116 module interfaces / 118 features (including the two
  module-less features log and unit_test_framework) / default 49-library closure /
  138 libraries consumable in total (116 modules + 2 compiled libraries consumed
  include-only + 20 pure include-only).
- **Platforms**: four CI legs covering windows (clang-msvc) / linux (gcc 16, llvm) / macos
  (llvm, arm64). mingw and real MSVC (cl) are not guaranteed (see §5 support matrix).
- **Licensing**: wrapper layer BSL; Boost upstream BSL; libclang Apache-2.0-LLVM.

## 2. import Usage

### 2.1 Dependency Declaration (git dep)

```toml
# Default: 49-library closure
[dependencies]
boost.boost = { git = "https://github.com/ZheFeng7110/boost-module", tag = "b1.91.0w0.0.0-preview" }

# Pick a few libraries only (default-features = false disables the default set)
[dependencies.boost.boost]
git = "https://github.com/ZheFeng7110/boost-module"
tag = "b1.91.0w0.0.0-preview"
default-features = false
features = ["optional", "json"]

# Everything
boost.boost = { git = "https://github.com/ZheFeng7110/boost-module", tag = "b1.91.0w0.0.0-preview", features = ["all"] }
```

Once the first stable release is out, the package will be published on the mcpp package
index; for now, use git dependencies.

> **Do not use `features = ["all"]` with clang**: all 117 CMIs total about 2.98GB, exceeding
> clang's 2^31 source-location limit, which fails with "ran out of source locations"; there
> is no flag to raise it. **If you need everything, import libraries one by one**
> (user decision 2026-09-08); the same limit has not been verified on the gcc side.

### 2.2 Three Consumption Modes

1. **Module import** (116 libraries): `import boost.<lib>;` / `import boost;`.
   `import boost;` is an umbrella module dynamically generated by build.mcpp that re-exports
   exactly the currently active libraries; it is a legal empty shell when nothing is active.
   The API spelling is identical to upstream; free operators are explicitly exported and
   friend operators work through ADL.

   ```cpp
   import boost.filesystem;   // single library
   import boost;              // umbrella (re-exports the currently active libraries)
   ```

2. **Pure include-only** (20 libraries): no feature, no module — just `#include` the
   upstream headers. This can be mixed with module imports in the same TU (the standard
   allows it). Macro APIs (BOOST_PP_/BOOST_FOREACH/BOOST_DESCRIBE_*/BOOST_OPENMETHOD*/
   BOOST_SCOPE_EXIT_* etc.) can only ever come from includes — macros are
   preprocessor-level API and never cross module boundaries.

   ```cpp
   #include <boost/preprocessor/cat.hpp>   // macro API: include only
   #include <boost/foreach.hpp>
   import boost.core;                      // modularized libraries import as usual; both coexist
   ```

3. **Compiled libraries consumed include-only** (2 libraries: log, test): the feature keeps
   compiling and linking the library TUs, but there is no
   `export module boost.<lib>;` module interface.
   - **log**: `--features log` + `#include <boost/log/...>` + link the library TUs.
   - **test** (`unit_test_framework`): **two consumption forms, which must not be linked
     together** (the framework TUs and the included aggregated implementation have
     conflicting symbols — pick one):

     | Form | feature | include | linking |
     |---|---|---|---|
     | Compiled framework (officially recommended) | `--features unit_test_framework` | `<boost/test/unit_test.hpp>` (+ `BOOST_TEST_NO_MAIN` + `<boost/test/impl/unit_test_main.ipp>` to pull in the runner, or supply your own main) | framework TUs from the package |
     | Header-only (officially optional) | not enabled | `<boost/test/included/unit_test.hpp>` (aggregate header, includes main) | none |

### 2.3 Version Constants (`boost.version`)

```cpp
import boost.version;    // in the default set; import boost; re-exports it automatically
static_assert(boost::BOOST_VERSION == 109100);
static_assert(boost::BOOST_LIB_VERSION[0] == '1');
```

The macro form (`#if BOOST_VERSION >= 109100`) requires the consumer to
`#include <boost/version.hpp>` themselves; **within the same TU, the macro definitions and
the module spelling are mutually exclusive** (the macro expands
`boost::BOOST_VERSION` → `boost::109100`) — pick one.

## 3. Feature-based Selective Build Semantics

Each library maps to one feature (generated by `scripts/gen_features.py`; do not edit by
hand): 116 module features (T0 26 + T1a 61 + T2 16 + T1b 12 + `version` 1) +
2 module-less features (log, unit_test_framework).

- **The default set is the 49-library closure** (`[features].default`, grows automatically
  with module import edges): `mcpp build` / `mcpp test` cover the core surface (19 former
  core libraries + infrastructure libraries such as config/assert/utility/move +
  `boost.version`).
- **Opt-in libraries**: all other features must be activated explicitly,
  `mcpp build --features <lib,...>`; consumers use `features = [...]` +
  `default-features = false`.
- **implies closure**: features may declare `implies` (transitive closure); e.g.
  `--features log` pulls in the link dependencies (the implies of log/utf are pinned by
  hand, `EXTRA_IMPLIES = {"parser": ["charconv"]}`).
- Feature changes alter cflags → BMI/build caches invalidate automatically;
  the `MCPP_FEATURE_<NAME>` macros are visible only at this package's compile time (not
  propagated to consumers).
- Consumers must provide their own std surface (`import std;` or includes) — operators on
  boost entity signatures that reference std types are not visible in a pure-import TU (by
  design).

## 4. Known Limitations (consumer notes)

### 4.1 Toolchain/Standard Hard Limits

| Limitation | How to consume |
|---|---|
| clang `--features all` exceeds the 2^31 source-location cap (~2.98GB CMI) | **Import libraries one by one (recommended)** (user decision 2026-09-08); not verified on the gcc side |
| Feature macros are all fixed at build time | Consumers cannot customize any BOOST_* feature macros |
| filesystem locked to v3 API; thread locked to v2 API (`unique_future`); stacktrace basic | Spell per the corresponding upstream version |
| algorithm has no regex surface (gcc abi-tag) | For regex needs, include the upstream headers separately |
| iostreams external backends (zlib/gzip/bzip2/lzma/zstd) and cobalt ssl not packaged (OpenSSL) | Provide external dependencies yourself |
| math tr1, container dlmalloc/alloc_lib, process aggregate headers not packaged | Use the main API surface |
| log event_log hand-written mc.exe stub, dump_avx2/ssse3 not packaged | Platform trims |
| atomic sse41 uses probe-fail fallback | Automatic |
| type_erasure `any<>` dynamic-dispatch path cannot be instantiated by clang-msvc module consumers | Module surface / concept templates work |
| `numeric::interval<double>` module surface not instantiable (explicit specialization of default policies) | Include the header file |
| Anonymous-namespace forwarders not exported: range pipe syntax (`vec \| reversed`), multi_array `boost::extents` | Use the functional form / container-style construction |
| Internal-linkage constexpr objects not exportable — residual surface: accumulators `extract::*` (use `extract_result<>`), mqtt5 `prop::*` (use `integral_constant`) | Use the alternative spellings |
| libclang generation blind spots: pfr::tuple_size_v, hana int_c and other variable templates missing (class-template alternative spellings) | Use the alternative spellings |

### 4.2 gcc 16.1 Defect Family and the Three-Mode Consumption Rule

gcc 16.1's module implementation has a defect family (see consolidated design §6.1):
exception CMI pendings (library already downgraded to include-only), variant
`apply_visitor` free-function ICE (use the member version), missing clone_impl thunk for
consumer-defined exceptions, CMI/GMF merge conflicts, etc.

**Three-mode gcc consumption rule**: ① plain import; ② import + supplemental standard
headers (`<new>`/`<typeinfo>`); ③ pure include. Re-verify the gcc consumption surface each
time a new library is onboarded or consumed.

### 4.3 Pure include-only Library List (20 libraries, no feature no module)

- **T3 macro-driven (16)**: preprocessor / mpl / fusion / proto / spirit / xpressive /
  typeof / vmd / phoenix / parameter / metaparse / function_types / tti / local_function /
  msm / foreach — their public API is a macro family, which named modules can never export.
- **Downgraded (4)**: exception (gcc 16.1 CMI pendings), describe / openmethod /
  scope_exit (macro-heavy + gcc 16.1 include+import mixed-use ODR redefinition).

### 4.4 M13 Deferred List (11 libraries, not supported in the preview)

External-dependency/asm libraries remain deferred (user decision 2026-09-08); zero changes
this cycle:

> context / fiber / coroutine (asm), locale (ICU), mpi, python, parameter_python,
> graph_parallel, compute (OpenCL), mysql / redis (OpenSSL)

## 5. Support Matrix

| Platform / compiler | Status |
|---|---|
| linux + gcc 16.1 | CI leg ✅ (affected by the §4.2 defect family; verified per library) |
| linux + llvm (clang) | CI leg ✅ |
| macos + llvm (clang, arm64) | CI leg ✅ (precise exception catch limited by Mach-O typeinfo; needs a `std::exception` catch-all) |
| windows + clang (clang-msvc flavor) | CI leg ✅ |
| windows + real MSVC (cl) | **never verified**, not guaranteed |
| windows + mingw gcc | no CI leg, **not guaranteed** (known: thread `sleep_for` hangs, url `BOOST_URL_RETURN_EC` macro conflict) |

## 6. Helper Scripts

The scripts depend on **libclang** (`scripts/gen_exports.py` / `scripts/gen_audit.py` use it
to parse the AST of Boost headers). If libclang is not installed, install it first:

```bash
pip install libclang        # or set LIBCLANG_PATH to the libclang.dll of a local LLVM
```

Users with [uv](https://docs.astral.sh/uv/) installed need no manual setup — the scripts
carry PEP 723 inline metadata, and `uv run` automatically creates a temporary environment
with libclang:

```bash
uv run scripts/gen_exports.py --scan                 # regenerate scripts/libs.json
uv run scripts/gen_exports.py                        # generate export lists for all target libraries
uv run scripts/gen_exports.py --libs optional system --emit-cppm
uv run scripts/reapply_hand_edits.py                 # replay hand edits after regeneration (.cppm deviations + .inc platform guards + deps/boost vendored patches)
uv run scripts/gen_features.py                       # regenerate the [features] block of mcpp.toml + scripts/features.lst
uv run scripts/gen_audit.py                          # static-inline / internal-linkage audit
uv run scripts/import_boost.py                       # re-import the official boost tarball
uv run scripts/reapply_hand_edits.py          # import_boost wipes the vendored patches; re-run this to replay them (mandatory!)
```

> Without uv, run `python scripts/xxx.py` as usual (the shebang stays plain
> `#!/usr/bin/env python3`; the inline metadata is just a comment).

Script responsibilities:

- `scripts/import_boost.py` — downloads the official `boost_1_91_0.tar.gz` with a pinned
  SHA-256, trims it, and imports into `deps/boost/` (`boost/boost/` aggregate include root +
  `libs/` etc.).
- `scripts/gen_exports.py` — enumerates a library's public headers via the libclang AST →
  collects `boost::` external-linkage entities → dependency closure (e.g. filesystem brings
  in system::error_code) → cross-module deduplication (first wins) → produces
  `src/gen_exports/<lib>.inc` (the `export namespace boost { using ...; }` list), `*.deps`
  (`export import` hints), and the `src/<lib>.cppm` draft.
- `scripts/gen_features.py` — generates the `[features]` block of `mcpp.toml` (one feature
  per library, `sources` = the library's `.cppm` + compiled-library TU globs;
  log/unit_test_framework are module-less features with only library TUs, C1;
  `boost.version` is a LIBS_SPECIAL form: has `.cppm` but no TU globs / no `.deps`, C5)
  from `libs.json` + `src/gen_exports/*.deps`, plus `scripts/features.lst`
  (consumed by build.mcpp).
  The default set is the 49-library closure; everything else is opt-in
  (`--features <feature>` to activate explicitly).
- `scripts/gen_audit.py` — outputs the list of static-inline / internal-linkage entities
  needing manual replacement; `--macros` counts the macro-injection surface of each
  library's public headers (verification input for the M10 T3 include-only list).
- `scripts/reapply_hand_edits.py` — after regenerating `.inc`/`.cppm`, replays all hand
  edits in one shot (core/scope/algorithm gcc workarounds, `.inc` platform guards, algorithm
  header comment conventions), idempotently.
  String patches are stored as unified diffs in `scripts/patchs/<module>.patch` (one patch
  file per module), applied with `git apply` and checked for idempotency via reverse
  apply; `.inc` platform guards, new vendored files, and the "M3 final form" git restores
  remain in-script logic.
  It also replays the vendored header patches under `deps/boost/` (M5 B' / M9 / M11 / M12,
  22 patch files + 1 new file in total) — re-vendoring via `import_boost.py` restores those
  files to their upstream originals, so this script must be re-run after any re-import
  (rollup doc §3.7#1).
