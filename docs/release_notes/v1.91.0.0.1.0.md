# Release Notes — v1.91.0.0.1.0

> Date: 2026-09-22 · Target upstream: Boost 1.91.0 (`BOOST_VERSION 109100`)
> **Stable minor release** (modules wrapper version 0.1.0). Module/feature counts and the
> consumable surface are **identical** to `1.91.0.0.0.1`; the changes are a package-identity
> migration, automated release packaging, and example refresh. See §4 for the full delta.

## 1. What Is This

C++23 named modules wrapper for the Boost libraries built with the
[mcpp](https://github.com/mcpp-community/mcpp) build tool: consumers write
`import boost.filesystem;` (or the umbrella `import boost;`); the API spelling is identical
to upstream, no `#include` needed.

This release follows `1.91.0.0.0.1` (2026-09-22). It does **not** change the module surface;
it changes the mcpp dependency identity and moves release packaging into CI. For the full
library-by-library known-limitation disclosure, see the first stable release notes
([`b1.91.0w0.0.0`](b1.91.0w0.0.0.md)); the still-valid subset applies unchanged (§5).

- **Platforms**: four CI legs covering windows (clang-msvc flavor) / linux (gcc 16, llvm) /

  `import boost;`).

## 3. Package Identity Change (breaking for consumers)

The mcpp dependency identity changed from `boost.boost` to **`ZheFeng7110.boost`**:

| | Old | New |
|---|---|---|
| `[package].namespace` | `boost` | `ZheFeng7110` |
| consumer declaration | `boost.boost = { ... }` | `ZheFeng7110.boost = { ... }` |

This is the package namespace (`namespace` + `name`), independent of the C++ side: the module
names (`import boost.<lib>;`), the umbrella `import boost;`, and the exported `boost::`
namespace are **unchanged**. The version/tag scheme is also unchanged
(`v1.91.0.0.1.0` here).

> **Action for existing consumers**: rename the dependency key from `boost.boost` to
> `ZheFeng7110.boost` (both the `[dependencies]` inline form and the
> `[dependencies.<key>]` table form), and update the `tag = ...` / `rev = ...` to
> `v1.91.0.0.1.0` if pinning by version.

## 4. Changes Since v1.91.0.0.0.1

- **Package namespace rename** — `[package].namespace` is now `ZheFeng7110`, so the mcpp
  dependency identity is `ZheFeng7110.boost` instead of `boost.boost`; the README / usage /
  architecture docs and the three examples were synced (see §3). No C++ module or export
  change.
- **Automated GitHub Release workflow** — `.github/workflows/release.yml` now runs on a tag
  push: it extracts `docs/release_notes/<tag>.md` as the release body (the run fails if the
  file is missing), runs the new `scripts/package-source.sh` to build source archives
  (`.zip` / `.tar.gz` / `.tar.xz` / `.7z` + `.sha256` checksums), and attaches them to a
  release titled `Release <tag>`; tags ending in `-preview` are marked prerelease. The
  release runbook (en + zh) documents the automated flow and the manual fallback.
- **Example refresh** — `examples/git_dep_usage` points at the current revision and its
  stale committed `mcpp.lock` was removed (mcpp re-resolves it).

No module, feature, count, or API changes; no changes to the supported library set.

## 5. Known Limitations

Unchanged from the first stable release and disclosed in full there because the mcpp
package-index integration (T3) is still pending. The still-valid entries (toolchain hard
limits, the gcc 16.1 defect family, pure include-only library list, platform/coverage gaps,
and the 11 M13-deferred libraries) are itemized in
[`b1.91.0w0.0.0§4`](b1.91.0w0.0.0.md#4-known-limitations-full-disclosure) and
[architecture doc §4](../architecture.md#4-known-limitations-consumer-notes).

## 6. Packaging Status

The stable release bar normally includes publishing on the mcpp package index (the `T3`
`boost.lua` integration + registry consumption probe). That work remains scheduled after this
tag (it depends on the immutable tag), so this release is consumed through the git
dependency documented in the user guide. Known-limitation disclosure is kept full rather
than reduced for that reason. Source archives are now produced automatically by the release
workflow (§4).

## 7. Reporting Issues

Before filing an issue, distinguish a **wrapper problem** from a **compiler defect**; the
guidance is unchanged from
[`b1.91.0w0.0.0§7`](b1.91.0w0.0.0.md#7-reporting-issues). In short: gcc 16.1 and
clang/llvm ICEs and source-location caps are compiler defects (attach a minimal
reproduction); suspect wrapper problems should attach compiler + platform + dependency
declaration + a minimal reproducing TU; mingw / real MSVC feedback is welcome.
