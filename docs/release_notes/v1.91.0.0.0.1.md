# Release Notes — v1.91.0.0.0.1

> Date: 2026-09-22 · Target upstream: Boost 1.91.0 (`BOOST_VERSION 109100`)
> **Stable patch release** (modules wrapper version 0.0.1). Module/feature counts and the
> consumable surface are **identical** to `1.91.0.0.0.0` (previously tagged
> `b1.91.0w0.0.0`); the changes are a version/tag naming migration and a Windows build
> fix. See §4 for the full delta.

## 1. What Is This

C++23 named modules wrapper for the Boost libraries built with the
[mcpp](https://github.com/mcpp-community/mcpp) build tool: consumers write
`import boost.filesystem;` (or the umbrella `import boost;`); the API spelling is identical
to upstream, no `#include` needed.

This patch follows the first stable release `1.91.0.0.0.0` (2026-09-21). It does **not**
change the module surface; it re-cuts the same contents under the corrected numeric
version/tag scheme and folds in a Windows-only build fix. For the full library-by-library
known-limitation disclosure, see the previous release notes
([`b1.91.0w0.0.0`](b1.91.0w0.0.0.md)); the still-valid subset applies unchanged (§5).

## 3. Version / Tag Naming Migration (breaking for pinned consumers)

The version string changed from `b<boost>w<wrapper>` to a **six-segment numeric
`v<boost version>.<wrapper version>`**:

| | Old | New |
|---|---|---|
| git tag | `b1.91.0w0.0.0` | `v1.91.0.0.0.1` |
| `[package].version` | `b1.91.0w0.0.0` | `1.91.0.0.1` |
| consumer declaration | `tag = "b1.91.0w0.0.0"` | `tag = "v1.91.0.0.0.1"` |

mcpp's version grammar requires a digit first and rejects letters in the numeric core, so
the old string triggered a `not a version RANGE` warning at every consumer that referenced
it by version. The leading `v` belongs to the git tag only — `[package].version` and a
consumer's `version = "..."` must omit it; mcpp's publish convention prepends `v` when it
derives the tag/tarball URL. Historical tags (`b1.91.0w0.0.0*`) and their release
notes/changelog entries are left in place and remain immutable.

> **Action for existing consumers**: update the `tag = ...` (or `rev = ...`) in the
> dependency declaration to `v1.91.0.0.0.1`.

## 4. Changes Since b1.91.0w0.0.0

- **Version/tag naming scheme** — `[package].version` is now `1.91.0.0.0.1`, consumed by
  the tag `v1.91.0.0.0.1`; README / usage / architecture docs and the release runbook were
  updated to the numeric scheme (see §3).
- **Windows build fix (`BOOST_THREAD_BUILD_LIB`)** — the define moved from the private
  `[features.thread].flags` back to the base `[build].flags` (per-glob over
  `deps/boost/libs/thread/src/**`). `mcpp test` compiles all base `[build].sources`
  regardless of feature selection, so with `thread` inactive on Windows `win32/thread.cpp`
  referenced `tss_cleanup_implemented()` without the macro (its definition in `tss_pe.cpp`
  is gated by `BOOST_THREAD_BUILD_LIB`), failing to link. The per-glob form keeps the flag
  scoped to the thread library TUs and still never propagates to consumers.
- **Generator sync** — `scripts/gen_features.py` updated so the generated block stays
  consistent with the moved flag.

No module, feature, count, or API changes; no changes to the supported library set.

## 5. Known Limitations

Unchanged from `1.91.0.0.0.0` and disclosed in full there because the mcpp package-index
integration (T3) is still pending. The still-valid entries (toolchain hard limits, the
gcc 16.1 defect family, pure include-only library list, platform/coverage gaps, and the 11
M13-deferred libraries) are itemized in
[`b1.91.0w0.0.0§4`](b1.91.0w0.0.0.md#4-known-limitations-full-disclosure) and
[architecture doc §4](../architecture.md#4-known-limitations-consumer-notes).

## 6. Packaging Status

The stable release bar normally includes publishing on the mcpp package index (the `T3`
`boost.lua` integration + registry consumption probe). That work remains scheduled after
this tag (it depends on the immutable tag), so this release is consumed through the git
dependency documented in the user guide. Known-limitation disclosure is kept full rather
than reduced for that reason.

## 7. Reporting Issues

Before filing an issue, distinguish a **wrapper problem** from a **compiler defect**; the
guidance is unchanged from
[`b1.91.0w0.0.0§7`](b1.91.0w0.0.0.md#7-reporting-issues). In short: gcc 16.1 and
clang/llvm ICEs and source-location caps are compiler defects (attach a minimal
reproduction); suspect wrapper problems should attach compiler + platform + dependency
declaration + a minimal reproducing TU; mingw / real MSVC feedback is welcome.
