# Release Notes — v1.92.0.0.0.0

> Date: 2026-10-10 · Target upstream: Boost 1.92.0 (`BOOST_VERSION 109200`)
> **Stable release** (modules wrapper version 0.0.0; the first release for the Boost 1.92
> line). Module/feature counts and the consumable surface are the same shape as the previous
> line: **116 modules / 118 features / 49-library default closure**. The cycle re-imports
> upstream Boost 1.92.0 and regenerates the export surface, completes the release automation
> (GitCode mirror + mcpp package index), refreshes CI, and adds a macOS exception-handling
> workaround. See §3 for the full delta.

## 1. What Is This

C++23 named modules wrapper for the Boost libraries built with the
[mcpp](https://github.com/mcpp-community/mcpp) build tool: consumers write
`import boost.filesystem;` (or the umbrella `import boost;`); the API spelling is identical
to upstream, no `#include` needed.

This is the first stable release for the Boost **1.92.0** line. It follows
`1.91.0.0.1.0` (2026-09-22); the module surface is regenerated from the new upstream headers
but the module/feature counts and the consumable set are unchanged. The mcpp package-index
integration (T3) is now part of the automated release flow, so the package is consumable
through the registry as well as the git dependency (§5).

## 3. Changes Since v1.91.0.0.1.0

### 3.1 Upstream Boost 1.92.0 re-import and export regeneration

- **Vendored upstream bumped `1.91.0 → 1.92.0`** (`BOOST_VERSION 109200`,
  `BOOST_LIB_VERSION "1_92"`): `deps/boost/` re-imported from the official tarball, all
  vendored patches replayed (`scripts/reapply_hand_edits.py`), and the committed generated
  artifacts (`src/gen_exports/*.inc` / `*.deps`, `src/*.cppm`, `mcpp.toml [features]`,
  `scripts/features.lst`) fully regenerated.
- **Header-set rescan (`scripts/libs.json`)**: the 1.92 additions under target libraries were
  curated in (e.g. `asio/fwd.hpp`; 49 `container/experimental/segmented_*`; `graph` and
  `lockfree` additions), historical curated exclusions were restored, and libraries removed
  from the target set were dropped. The libraries whose exported surface actually changes are
  **asio / container / graph / lockfree**; the rest is unchanged.
- **`decimal` platform guards**: Boost 1.92 added `detail`/int128 entities that exist only
  under specific compilers/arches (`u256_add` / `add_carry_u64` under `__GNUC__`; the
  `BOOST_DECIMAL_DETAIL_INT128_HAS_FAST_DIV128` family, x86-64 GCC/Clang/MSVC). The MinGW
  snapshot exported all of them, so `import boost.decimal;` failed on macOS arm64 and
  windows-msvc; the affected `using` lines are now wrapped in the upstream conditions.
- **`stacktrace` feature** also compiles `deps/boost/libs/stacktrace/src/dump.cpp`
  (1.92 moved `this_thread_frames::collect` out of the header into a separate TU), keeping the
  `basic` surface linkable. `stacktrace` stays on the `basic` flavor.
- **`asio` vendored patch reduced** from 6 files to 2: upstream 1.92 already made the
  `prefer` / `query` / `require` / `require_concept` objects `inline constexpr` for C++17+,
  so only the `call_stack.hpp` / `keyword_tss_ptr.hpp` static-member definitions still need
  the `inline` fix-up.

### 3.2 macOS exception-handling workaround

- **Use Apple's linker on macOS** (`[target.macos.build]` → `-fuse-ld=/usr/bin/ld`).
  LLVM 22.1.8's `ld64.lld` can emit duplicate `__unwind_info` entries (a zero encoding
  shadowing a real one), which makes libunwind stop in phase one and leaves every handler —
  including `catch (...)` — unreachable. This showed up as a `program_options` invalid-value
  abort in CI; Apple's linker produces a correct binary. `ld64.lld` ignores
  `-no_compact_unwind`, so the linker swap is the workaround (upstream
  [LLVM issue 216154](https://github.com/llvm/llvm-project/issues/216154)).
- **`program_options` regression coverage split** into a module-side check
  (`tests/program_options.cpp`, still exercising the precise `invalid_option_value` catch on
  linux/windows/macOS) plus a dedicated include-only executable
  (`tests/program_options_invalid_value.cpp`). The test count is now **142** (was 141).

### 3.3 Release automation completed

- **GitCode mirror job**: on a stable or preview tag, after the GitHub Release is created the
  workflow force-syncs every branch/tag to the mirror `gitcode.com/ZheFeng7/boost-module` and
  publishes a matching Release whose notes come from `docs/zh/release_notes/<tag>.md`
  (title / prerelease flag / assets identical to GitHub).
- **mcpp package index (T3) registration**: for non-preview tags a new job prepends the
  released version to `pkgs/z/ZheFeng7110.boost.lua` on a branch of the `mcpp-index` fork and
  opens the upstream registration PR. This is the step that publishes the package on the mcpp
  index; the release title is now just the tag (the `Release ` prefix was dropped).

### 3.4 CI and docs

- **CI refresh**: mcpp pinned to `2026.10.8.1`; runner OS updated; Linux ARM64 (gcc) legs
  added; hosts without mcpp release binaries dropped (macOS x86_64, Windows ARM64, Linux
  ARM64 LLVM). The matrix is five test legs × groups A/B plus a gated examples job.
- **Docs/examples**: the mcpp package index is presented as the primary consumption channel
  (git dependency kept as the alternative, with the Mainland-China mirror noted);
  `examples/git_dep_usage` points at the 1.92 upgrade revision.

No module, feature, default-closure, or API-spelling change; the supported library set is
unchanged.

## 4. Known Limitations (still valid)

Kept concise for the stable release; the itemized list and per-library notes are in the
[architecture doc §4](../architecture.md#4-known-limitations-consumer-notes).

- **Toolchain hard limits**: clang's 2^31 source-location cap rules out `--features all`
  (~2.98GB of CMIs) — import libraries one by one; feature macros are build-time fixed except
  for the `backend-*` profile subset.
- **Fixed upstream flavors**: filesystem v3 / thread v2 / stacktrace basic.
- **Not packaged**: iostreams external backends (zlib/gzip/bzip2/lzma/zstd) and cobalt ssl
  (OpenSSL); math tr1; container `dlmalloc`/`alloc_lib`; process aggregate headers; log's
  hand-written `mc.exe` event-log stub.
- **gcc 16.1 defect family** (compiler bugs, worked around or avoided): exception CMI
  pendings, variant `apply_visitor` free-function ICE, missing consumer `clone_impl` thunk,
  CMI/GMF merge conflicts. See architecture doc §4.2 for the three-mode consumption rule.
- **Pure include-only set (20 libraries, no feature/module)**: 16 macro-driven
  (preprocessor / mpl / fusion / proto / spirit / xpressive / typeof / vmd / phoenix /
  parameter / metaparse / function_types / tti / local_function / msm / foreach) + 4
  downgraded (exception / describe / openmethod / scope_exit).
- **Platform gaps**: mingw (no CI leg; thread `sleep_for` hangs, url `BOOST_URL_RETURN_EC`
  conflict) and real MSVC (cl) are not guaranteed; macOS precise exception catch can still be
  limited by Mach-O typeinfo not merging across module boundaries.
- **M13 deferred (11 libraries)**: context / fiber / coroutine (asm), locale (ICU), mpi,
  python, parameter_python, graph_parallel, compute (OpenCL), mysql / redis (OpenSSL).
- **Upstream C++20 modules not enabled**: Boost 1.92 ships `modules/` in several libraries;
  this wrapper still exports its own `export using` layer and does not consume them.

## 5. Packaging Status

The stable release bar's mcpp package-index step (T3: descriptor integration + registry
consumption) is now automated: the release workflow registers the version in
`ZheFeng7110.boost` on the mcpp index and opens the upstream PR, and the docs present the
index as the recommended channel. Source archives (`.zip` / `.tar.gz` / `.tar.xz` / `.7z` +
`.sha256`) are produced by the release workflow, and the same assets are mirrored on GitCode.
Consumers may also continue to use the git dependency documented in the user guide.

## 6. Reporting Issues

Before filing an issue, distinguish a **wrapper problem** from a **compiler defect**:

1. **gcc 16.1 defect family** (§4) are compiler bugs; attach an upstream-reproducible minimal
   example and note the compiler version.
2. **clang/llvm issues** (e.g. the 2^31 source-location cap, the macOS `ld64.lld` unwind bug)
   are toolchain limits; the wrapper works around what it can.
3. **Suspected wrapper problems** (missing entities / spelling mismatch / link errors / docs
   contradicting behavior): attach compiler + platform + dependency declaration + a minimal
   reproducing TU.
4. Failures on mingw / real MSVC (not-guaranteed scope) are welcome as feedback.
