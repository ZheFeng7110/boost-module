# M2 生成器设计: gen_exports.py / gen_audit.py

> 日期: 2026-08-09 · 状态: 已确认 · 计划: boost-mcpp-module-plan.md M2
> 前置: M0 spike 结论 (导出写法/运算符规则/gcc 坑) + M1 官方 tarball 布局 (boost/boost/ 汇总根)

## 1. 目标与交付物

M2 交付**生成管线**而非模块层 (模块层是 M3/M4):

| 产物 | 说明 |
|---|---|
| `scripts/gen_exports.py` | 主生成器: AST 枚举 → 依赖闭包 → 去重 → `src/gen_exports/<lib>.inc` |
| `scripts/gen_audit.py` | 审计器: 输出需手工替代的 static-inline/内部链接实体清单 |
| `scripts/boost_common.py` | 两脚本共享: 目标库清单、头文件解析、bundle TU 构建、file→lib 映射、拓扑序 |
| `scripts/libs.json` | 27 个目标库的**头文件清单** (由 `gen_exports.py --scan` 启发式生成, 人工复核后固化, committed) |
| `src/gen_exports/<lib>.inc` | 每库一个 export using 列表 (committed, M3 的 .cppm 直接 include) |
| `src/gen_exports/<lib>.deps` | 被其他库模块认领走的实体来源 (提示 .cppm 需 `export import`) |
| `target/gen/` | 运行时报告: 实体统计、审计清单 (gitignored) |

## 2. 输入与头文件解析 (官方 tarball 布局)

M1 后**所有库头文件统一在 `deps/boost/boost/` 汇总根**下, `libs/<lib>/` 无 include/。
库 → 头文件映射无法从 `meta/libraries.json` 读取 (1.91.0 无 headers 字段), 采用:

1. **启发式默认**: 库 L 的头文件 = `boost/<L>/` 下全部 `*.hpp` + 存在时的单头 `boost/<L>.hpp`。
   已验证覆盖 26/27 库 (scope_exit 仅单头, tuple 仅目录, type_traits 双命中 …)。
2. **`scripts/libs.json` 固化**: `--scan` 按启发式落盘, 人工可增删 (例外: 个别库的
   公共头不在同名目录, 如 tuple 的 `boost/tuple.hpp` 属于 config 系, 不追)。
3. **`scripts/curated/<lib>.txt` 兜底**: 生成器看不见的实体 (宏生成、GMF 全局辅助
   `::operator new` 类), 每行一个限定名; 以 `::` 开头表示全局作用域实体。
   M0 已知的 gcc 坑 A 实体 (container placement_new) 不在 27 库内, 机制先就位。

**include 根 = `deps/boost/`** (消费者/M0 探针一致); 解析目标与 M0 探针一致:
`--target=x86_64-w64-mingw32 -std=c++23 -DBOOST_ALL_NO_LIB` (MSVC 未验证, 双编译器 CI 兜底)。

## 3. AST 枚举 (bundle TU 每库一次)

每库解析**一个 bundle TU**: `#include` 该库全部公共头 (与 M3 .cppm 的 GMF include 集
同构)。一次解析即获得该库全部声明 + 传递包含的依赖库声明, 实体去重靠 USR 天然消解
(同一实体在多个头中声明多次 → 同 USR)。

**收集条件** (全部满足才导出):
- 语义父链全为 `boost::*` 命名空间 (含 boost::detail 等内部命名空间 — 签名可达即导出,
  与上游 API 拼写一致)
- 外部链接: 非 `static`, 不在匿名命名空间
- 声明位置 (spelling file) ∈ 该库头文件集
- cursor 种类: class/struct 及模板、free function 及模板、变量(含 constexpr)、
  enum + enumerator、typedef/using 别名、concept

**跳过**:
- 类成员 (随类导出)、friend 声明、隐式实体
- **friend-in-class 运算符**: lexical parent 是类而 semantic parent 是命名空间 →
  跳过 (M0 §1: ADL 自动可达, friend 无法 using 导出)
- `extern template` 显式实例化声明/定义
- **自由运算符 (非 friend)**: 保留, 输出时以 `using boost::operator==;` 显式导出 (M0 §1)

**审计旗标** (gen_audit.py 输出, 不拦生成):
- `static` 自由函数 (内部链接, 不可导出) — 若被公共签名引用则 M3 需手工替代
- 匿名命名空间实体、外库模板的显式特化 (`template<> ...`) — 特化随主模板 using 导出
  会丢失, 需 curated 兜底确认
- 宏生成实体: 预处理后进 AST, 正常收集; 纯宏库 (preprocessor 等) 不在目标集

## 4. 依赖闭包

对收集实体集 BFS 遍历**签名引用**, 命中 boost 实体 (不限库) 则入闭包并递归:
- FunctionDecl: 返回类型、参数类型、模板参数默认实参
- ClassDecl: 基类
- Typedef/alias: 底层类型; VarDecl: 类型; 函数指针类型递归展开
- `get_canonical()` 消解别名; `type.get_declaration()` 取声明 cursor, USR 判等
- **只走声明不走函数体** (实例化需要体时由 GMF 提供 — M0 探针 4 已证链接模式成立)

**file→lib 映射**: 闭包实体按声明文件归到目标库; 非目标库文件 (boost/config、
boost/detail 等) 归入 "shared" 桶, 由**首个需求它的库**认领 (归属即 first-wins 的
一部分)。filesystem → system::error_code 即经此机制连带导出 (M0 输入 3)。

## 5. 跨模块去重 (first wins) 与处理顺序

- **拓扑序**: 文本扫描各库头文件的 `#include <boost/...>` → 库依赖图 → 依赖先处理
  (system 先于 filesystem)。环按目标库清单稳定顺序打破。
- **全局认领表**: 按拓扑序逐库处理, USR → 库 映射; 后处理的库对已被认领实体
  不再写入自己的 .inc, 记入 `<lib>.deps` → M3 在该库 .cppm 写 `export import boost.<home>;`
  (opencv-m 先例)。此方案下每个实体恰由一个模块导出, 无重复导出表。
- `--full-closure` 开关: 输出完整闭包 (自包含模块, 无 export import), 供对比调试。
- 同一 .inc 内 USR 去重 (同一实体多头声明只出一次)。

## 6. 输出格式 (M0 §1 验证拼写)

```cpp
// GENERATED by scripts/gen_exports.py — DO NOT EDIT
// lib=optional boost=1.91.0 target=x86_64-w64-mingw32 entities=N

export namespace boost {
  using boost::optional;
  using boost::operator==;
}

export namespace boost { namespace mp11 {
  using boost::mp11::mp_list;
} }
```

- 按实体声明命名空间路径分块 (每个命名空间路径一块, 嵌套块保持拼写)
- 运算符: `using boost::operator==;` (一次导入全部重载 — M0 §1)
- `.cppm` 骨架 (`--emit-cppm` 附加产物): GMF include 全部库头 → `export module` →
  include `.inc`; 最终形态由 M3 定稿 (宏一致性、module :private 取舍)。

## 7. gen_audit.py

输入: libs.json + 目标库清单。输出 `target/gen/audit/<lib>.txt` + stdout 汇总:
- namespace 级 `static`/内部链接函数 (static inline 审计目标 — M0 全树 3440 处集中在
  macro 系库, 27 目标库应为 0 或个位)
- 匿名命名空间实体、外库模板显式特化、friend 运算符 (信息性计数)
- 每实体: `文件:行 限定名 引用方(如有)`

## 9. 已知限制

- requires 子句/约束表达式不遍历 (libclang 暴露有限) → 实体可能缺闭包, 以编译期
  M3 smoke 兜底
- 宏驱动的实体只收集宏展开后的声明, 宏定义本身无法导出 (设计使然, 旁路头方案在 M3)
- 显式特化跨库不可达 (见 §3 旗标); MSVC 行为未验证

## 10. 实施记录 (2026-08-09, 与原设计差异)

实测过程中对原设计的关键修正 (均已落地):

1. **GMF 只含 root 头文件** (原设计 §2 的 detail 头文件集被推翻): upstream 的
   `detail/` 头文件不自足 (依赖 umbrella 头先建立宏与依赖, 例: optional_aligned_storage
   用 `boost::core::launder`, 而 optional.hpp 只在 union 实现路径下 include launder.hpp)。
   直接 include detail 头必然编译失败。**修正**: bundle TU / .cppm GMF = `boost/<lib>.hpp`
   汇总头 + 非 detail 根头; detail 头经传递包含进入 AST 且照常收集导出, 只是不直接 include。
   这也恰好等于消费者 `#include <boost/<lib>.hpp>` 所能触达的 API 面。
   验证: 修改后 optional/system 模块双编译器 (clang 22 / gcc 16) 构建 + 消费者通过。

2. **friend 检测必须走 FRIEND_DECL 子树**: friend-in-class 函数的 semantic parent 是
   命名空间 (namespace_chain 非空), 仅靠成员判定会漏; usr 索引遍历时跳过 FRIEND_DECL
   子树, 同时保留 lexical parent 是类的判定 (双重保险)。

3. **导出面 = 库属实体 + shared 实体**: 候选集 = bundle TU 中所有外部链接 boost::
   实体, 其声明文件归属为**本库或非目标库 (shared)**; 其他目标库的实体由依赖闭包拉取,
   且 `<lib>.deps` 用 **include 依赖图 ∪ 闭包认领** 双来源计算 (保证 boost::swap 这类
   不在任何公共签名里的实体也通过 export-import 链可达)。

4. **clang 构建模块不得加 `-fmodules`**: clang 22 + mingw 下 `-fmodules` 触发隐式
   模块化, 系统头 (malloc.h 等) 双重包含报 redefinition。**修正**: clang 用
   `--precompile` (产出 BMI) + `-c -fmodule-output=` (产出模块初始化对象) 构建,
   消费者 `-fmodule-file=boost.X=...pcm` + 链接模块 .o (GMF 有内容时必须)。gcc 侧
   用 `-fmodules` 正常 (无此问题)。M3 构建脚本按此执行。

5. **draft .cppm 不含 `module :private;`**: gcc 16 未实现 private module fragment
   (`sorry, unimplemented`)。且本设计无隐藏内容需求。

6. **消费者 std 表面** (M0 §3) 在 smoke 中复现: 消费者使用 std::pair 等须自带
   `#include <utility>` 或 `import std;`。

7. **审计口径**: static-inline 审计按文件归属 (前缀 home==lib) 扫整个 bundle AST,
   含 detail 子树 (root-only GMF 下 detail 头虽不直接 include, 其内部链接实体仍
   经模板体实例化触达消费者, 是 M3/M4 的手工替代候选)。实测: 27 库共 6 处
   (thread 1 + json 5, 均为 detail 内部辅助); M3 19 库为 0 (与 M0 预期一致)。

8. **枚举器**: 仅导出 unscoped 枚举的 enumerator (scoped 枚举成员随枚举本身可达),
   用 token 流检测 `enum class/struct`。errc_t 等 unscoped 枚举的 enumerator 全部
   正确导出并冒烟通过。

9. **clang 链接**: mingw 目标需 `-lpthread` (winpthreads, M0 §4 已注明)。

生成器产物: 27 库共 4009 个导出实体 (第二轮回修后); optional.inc / filesystem.inc
(deps: system 等) / json.inc (deps: system+variant2+core+mp11) 等, 全部
`export namespace boost { using ...; }` 拼写经 clang+gcc 模块构建验证。

## 11. 第二轮修复记录 (2026-08-09, 用户审查 algorithm/chrono 产物后)

用户指出的两个问题 (类内枚举 enumerator 泄漏) 暴露出一整类生成器缺陷, 修复如下:

1. **类内枚举的 enumerator 泄漏** (algorithm.inc 的 `isref::value_type::value` /
   `local_counted_base::count_type::initial_`, chrono.inc 的匿名枚举): ENUM_CONSTANT_DECL
   分支只查了 scoped 判定, 跳过了命名空间作用域检查。**修复**: 枚举的 namespace_chain
   为空 (枚举在类内) → 跳过 (enumerator 是类成员, 随类导出); 且这类实体 ns=[] 会落入
   空命名空间组, 输出成孤立 `export` + 后续 using 的畸形块 —— `export` 关键字只修饰
   紧邻一条声明, 其余行退化为未导出的全局 using (这就是"只导出了第一行"的原因)。

2. **匿名枚举的 qname 含 libclang 显示名** `(unnamed enum at <file>:<line>:<col>)`:
   qualified_name 对匿名枚举跳过其名 (命名空间作用域匿名枚举的 enumerator 是命名空间
   成员, `using boost::foo::use_long;` 直接可达)。

3. **显式特化不可导出**: `template<> ...` 的 specialization 有外部链接但无法 using
   导出; `clang_getSpecializedCursorTemplate` 对它们返回 null (对显式实例化才有效)。
   **修复**: token 流检测声明前导 `template< >` (空模板参数列表)。

4. **`_is_scoped_enum` 的 token 方案对宏生成枚举失效**: boost::thread 的
   `BOOST_SCOPED_ENUM_START(launch)` 展开的 `enum class` 在宏展开区内, extent 上
   无 token。**修复**: 用 `clang_EnumDecl_isScoped` C API (实测 launch/plain/scoped
   三类全部正确)。

5. **根头文件并非按名有序**: chrono 的 duration_get.hpp 使用 duration_units.hpp 却
   不 include 它 (上游两者都经 chrono/io.hpp 聚合头进入) —— 字母序 GFM 必然失败。
   **修复**: GFM = 头文件 include-DAG 的**源点** (不被集合内任何头 include 的聚合入口,
   环上取代表), 聚合头按上游顺序拉入其余全部。

6. **libclang 缺失头报告不可靠** (双向): 同一 `#include <unicode/utypes.h>` 缺失,
   裸头单独解析报告 fatal, 经 boost/config.hpp 链进入时静默; 反之 vexing-parse 幻影
   (cpp_regex_traits.hpp:966 的局部变量被报成外部链接命名空间函数) 只有 libclang 可见。
   **修复**: 双保险 —— (a) bundle 增加 **clang++ 驱动子进程 gate** (权威), 失败时按
   stderr 指认的头文件从 GFM 迭代裁剪重试 (线程的 pthread/win32 平台替代头、regex 的
   ICU 头均由此自动剪除); (b) 词法上下文检查: 声明实体的 lexical parent 必须在
   命名空间/类/枚举/TU 中 (排除函数体内的局部声明幻影)。

7. **json 的 src.hpp 必须留在 GFM**: json 1.91 的 charconv 实现 (.ipp) 只经
   `boost/json/src.hpp` 进入 (官方文档要求的单 TU 模式) —— 最初按"构建辅助头"排除后
   浮点解析实现丢失。**修复**: 保留 src.hpp (url 的 src.hpp 是 #error, 由 standalone
   过滤器自动剔除)。json 消费者冒烟 (parse "3.25" + serialize) 通过, 证明实现随模块
   对象链接。

8. **libclang 绑定两代 API**: uv 解析的 bindings 用 `get_tokens(extent=...)`,
   系统 python 的旧版用 `ranges=[...]` —— tokens_of 双签名兼容; `--scan` 的
   standalone 过滤器按解析后路径比较 (libclang 报相对路径, 此前前缀比较恒不命中,
   导致 rope_traits/ICU 头全部漏网)。

9. **审计性能**: 全 AST 递归对每个节点做 file 查询 (数千万次 C 调用) 导致 27 库
   30+ 分钟; **修复**: 表达式/语句节点只递归不做文件检查, 声明节点才做 —— 3 分钟
   完成。final 结果: static=6 (thread 1 + json 5, 均为模块 TU 内部辅助, 非模板体
   实例化场景, M4 无需替代)、specs=654 (显式特化, M3 审查)、friends=270 (ADL)。

最终状态: 27/27 模块 clang 预编译通过; optional/system/algorithm/json 消费者
clang 链接运行通过; gcc 模块构建通过 (消费者侧 std 表面冲突为 M0 §2 坑 B, M3 用
`import std;` 路径)。
