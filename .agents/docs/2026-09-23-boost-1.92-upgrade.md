# Boost 1.92.0 上游升级 (vendored 重导 + 产物重生成)

> 日期: 2026-09-23 · 状态: 实施完成 · 分支 `b1.92.0wdev`
> 范围: 把 `deps/boost/` 从 Boost 1.91.0 升级到 1.92.0，并重放 vendored 补丁、
> 重新生成 `src/gen_exports/*`、`src/*.cppm` 草稿、`mcpp.toml [features]` 与
> `scripts/features.lst`，同步全部版本元数据。
> 关联: 架构汇总 [`2026-09-08-consolidated-design.md`](2026-09-08-consolidated-design.md) §3.1/§3.5/§3.6，
> mingw sysroot 引导 [`2026-09-19-mingw-sysroot-bootstrap.md`](2026-09-19-mingw-sysroot-bootstrap.md)。

## 1. 背景与目标

维护线从 Boost 1.91.0 切到 1.92.0。`scripts/import_boost.py` 已由维护者手动把
`VERSION`/`PIN_SHA256` 改为 1.92.0 并执行导入，得到 pristine 的
`deps/boost/`。但导入会抹掉全部 vendored 修补，且已提交的生成物
（`.inc`/`.deps`/`.cppm`/`mcpp.toml`）都是 1.91 头文件快照。本次目标即按仓库
既有生成管线把其余文件适配到 1.92.0。

## 2. 升级流程（可复现）

```bash
# 0. 维护者已改 import_boost.py 的 VERSION/PIN_SHA256 并导入 deps/boost/
uv run scripts/reapply_hand_edits.py        # 重放 vendored 修补（导入后必做）
uv run scripts/fetch_mingw_sysroot.py       # 固定 mingw-w64 14.0.0 sysroot
LIBCLANG_LIBRARY_PATH=<完整 LLVM lib 目录> \
  uv run scripts/gen_exports.py --emit-cppm # 全量重生成 .inc/.deps/.cppm
uv run scripts/reapply_hand_edits.py        # 对新生成绩重放 src 侧手编/守卫/恢复
uv run scripts/gen_features.py              # 重写 mcpp.toml [features] + features.lst
uv run scripts/gen_features.py --check      # 归零校验
```

注意：生成器要求 `LIBCLANG_LIBRARY_PATH` 指向**完整 LLVM**（而非 pip
`libclang` wheel 的 `native/`），否则 libclang 找不到自带 resource dir
（`lib/clang/<ver>/include`），`mm_malloc.h` 链断裂、std 表面静默退化
（`boost_common._append_resource_dir` 注释）。

## 3. 本轮的关键发现与修复

### 3.1 asio vendored 补丁锚点漂移（上游已自行修复一半）

1.92 上游把 `prefer/query/require/require_concept` 的 TU-local 对象放进
`#if defined(BOOST_ASIO_HAS_INLINE_VARIABLES)` 分支，C++17+ 走
`inline constexpr`，仅 `#else` 保留匿名命名空间的 `static constexpr`。
本项目编译为 C++23，`BOOST_ASIO_HAS_INLINE_VARIABLES` 恒为 1，故这 4 个
hunk（把匿名命名空间改成 inline 变量）已无必要 —— 删除。

`call_stack.hpp` / `keyword_tss_ptr.hpp` 两个静态成员定义的 `inline` 化仍然
需要，保留。`scripts/patchs/asio.patch` 因此从 6 文件缩为 2 文件。

### 3.2 stacktrace 的 `this_thread_frames::collect` 链接失败（真行为变化）

1.92 把 `basic.cpp` 末尾的 `#include <boost/stacktrace/safe_dump_to.hpp>`
删掉，新增 `src/dump.cpp`（上游 `boost_stacktrace_basic` 现在链
`boost_stacktrace_dump`）。`collect_unwind.ipp` 里的
`this_thread_frames::collect` 定义随 `safe_dump_to.hpp` 只在 `dump.cpp` /
`from_exception.cpp` 中出现。

本项目 stacktrace feature 只编 `basic.cpp`，故测试链接报
`undefined reference to ...this_thread_frames::collect`。修法：
`scripts/gen_features.py` 的 `COMPILED_TU_GLOBS["stacktrace"]` 增加
`deps/boost/libs/stacktrace/src/dump.cpp`。不采用 `from_exception.cpp`，
因为它会 interpose `__cxa_allocate_exception`，属上游独立的
`boost_stacktrace_from_exception` 库，超出 basic 面。

### 3.3 `restore_from_git` 与索引的一致性要求

`reapply_hand_edits.py` 的 "M3 final form" 用 `git checkout -- <file>` 从
**索引**恢复手维护文件。升级期间索引仍是 1.91 状态，重放会把刚更新的
`src/core.cppm`（注释）、`src/gen_exports/{algorithm,flyweight}.inc`（头注释）
拉回 1.91。处理：先把工作区更新为 1.92 并 `git add -A` 使索引=工作区，再跑
重放即幂等。这是仓库"生成物提交后以索引为准"流程的固有语义，非缺陷。

### 3.4 生成物头注释版本

`gen_exports.py` 的 `// lib=... boost=1.91.0 ...` 格式串改为 1.92.0；已提交的
115 个 `.inc` 头注释同步替换（含被 `restore_from_git` 冻结的 2 个）。
